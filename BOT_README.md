# 🎌 Аниме-бот AniLibria → Telegram (MTProto, файлы до **2 ГБ**)

Полноценный бот для просмотра аниме: ищет тайтлы через **публичный AniLibria / AniLiberty API v1**,
сервер сам качает HLS-поток, собирает **MP4** через ffmpeg и отправляет его в Telegram
**файлом до 2000 МБ (2 ГБ)**.

> Прямой ответ на главный вопрос: **это MTProto-клиент (Pyrogram) с bot_token, а не Bot API.**
> Обычный Bot API (`api.telegram.org`) режет файлы до 50 МБ на отправку и 20 МБ на скачивание.
> MTProto-клиент (схема «userbot», как у @urluploadbot и подобных) даёт лимит **2000 МБ на файл**.
> Токен и `api_id/api_hash` **вшиты прямо в код** (`config.py`, `api_keys.py`).

## 🚀 Быстрый запуск

### Вариант 1 — Docker Compose (рекомендую)

```bash
docker compose up -d --build
docker compose logs -f
```

Данные (кэш видео, сессия MTProto, SQLite с file_id) лежат в томе `anime_data` → `/data`
и не теряются при перезапуске/пересборке.

### Вариант 2 — обычный docker

```bash
docker build -t animebot .
docker run -d --name animebot --restart unless-stopped \
  -v anime_data:/data \
  -e OWNER_ID=<твой_id_из_/id> \
  -e MAX_FILE_MB=2000 \
  animebot
```

### Вариант 3 — без докера (проверка на сервере)

```bash
apt-get update && apt-get install -y ffmpeg
pip install -r requirements.txt
python anime_bot.py --check     # проверит ffmpeg, SQLite и API AniLibria
python anime_bot.py             # запуск бота
```

### Хостинги (Railway / Render / Fly / VPS)
* Dockerfile в корне — хостинг подхватывает его автоматически.
* Том (Volume) монтируй в **`/data`** — иначе кэш и сессия будут теряться.
* Для PaaS, которым нужен «живой» порт, задай `HEALTH_PORT=8080` (или `PORT`) — бот поднимет
  микро-эндпоинт `/health`, а бот при этом продолжит работать как обычно.
* Настрой `OWNER_ID` (узнать: команда `/id` в боте) — откроется `/stats` и очистка кэша.

## 🎛 Возможности бота

**Поиск**
* Инлайн-режим (единственный способ искать): `@ваш_бот наруто` в любом чате — карточки тайтлов с постерами.
* Результат инлайна — **обычная карточка** (иконка = оригинальный постер): тап мгновенный,
  без «галочки» и предпросмотра файла. Кнопка «▶️ Смотреть» открывает бота **сразу на выборе серии**.
* Если карточку отправить **прямо в чат бота**, он сам открывает этот тайтл (список серий) —
  одно нажатие, ничего дополнительно подтверждать не нужно.
* Обычный текст в чате бота намеренно игнорируется — поиск только через инлайн.
* Кнопка «🔍 Поиск» присылает короткую подсказку и инлайн-кнопку «Открыть поиск».
* Обычная (постоянная) клавиатура Telegram внизу экрана: **⭐ Избранное · 🔍 Поиск · ▶️ Продолжить**.
  «Продолжить» открывает следующую серию последнего просмотра.
* Инлайн-меню: 🆕 Новинки, 🎲 Рандом, ⭐ Избранное, 🕓 История, 📁 Мои файлы, ⚙️ Качество, ❓ Помощь.

**Релиз и серии**
* Карточка: постер, год, тип, число серий, жанры, описание, доступные качества, ссылка на AniLibria.
* Кнопки карточки: **«▶️ Смотреть»** (сразу выбор качества 1-й серии), **«📺 Все серии»** (список серий),
  ⭐ Избранное, 🔗 AniLibria, 📤 Поделиться, 🏠 Меню.
* Список серий со страницами (по 12 штук), выбор серии → выбор качества 1080 / 720 / 480.

**Скачивание и отправка (быстро)**
* Сегменты HLS качаются **параллельно и адаптивно**: **безопасный старт с 3 соединений**,
  первая тройка сегментов прошла без лимитов — быстрый разгон до 6, дальше по одному до
  `HLS_CONNECTIONS` (8). Одна связь отдаёт ~200–500 КБ/с (серия «ехала» десятки минут),
  несколько — уже МБ/с. Если 429 прилетел сразу — бот мгновенно уходит на 1 связь с паузами,
  а не устраивает 429-шторм.
* **Прогресс не «залипает» на 0%.** Отдельный heartbeat каждые 2 секунды обновляет сообщение,
  пока бот ждёт CDN: «CDN тормозит — пауза N с (соединений: M)». Поэтому даже при паузах видно,
  что работа идёт.
* **CDN AniLibria ограничивает всплески (429/403).** Поэтому: запросы разносятся джиттером,
  при лимите бот читает `Retry-After`, ставит общую паузу и **вдвое сбрасывает число потоков**,
  при упорном лимите — докачивает по одной связи. Настройки: `HLS_JITTER`, `HLS_MAX_RATE_HITS`,
  `HLS_BACKOFF_BASE`, `HLS_RETRY_AFTER_MAX`, `HLS_LONG_PAUSE`, `HLS_MAX_FORBIDDEN`.
* **Докачка с места:** скачанные сегменты сохраняются, поэтому после сбоя/отмены повторное
  нажатие кнопки качает только недостающее, а не всё заново.
* Если ссылка на поток успела истечь (403 на плейлисте), бот сам берёт свежую из API и повторяет.
* Дальше — **remux без перекодирования** (`-c copy`, качество 1:1, моментально) уже с локальных
  файлов; при проблемах — AAC-звук, затем транскод x264. Если параллельная схема недоступна,
  бот сам откатывается на прямое чтение потока ffmpeg.
* Прогресс-бар в процентах (скачивание → загрузка в Telegram), скорость, ETA, кнопка отмены.
* Очередь задач (`CONCURRENT_DOWNLOADS`), лимит качества, авто-подбор качества поменьше,
  если файл не влезает в 2000 МБ.
* «🔁 Смотреть подряд» — серии идут одна за другой до конца сезона.
* Кэш `file_id`: повторный запрос той же серии — **мгновенно**, без скачивания.
* **Канал-хранилище (`TELEGRAM_CHANNEL_ID`, по умолчанию `-1004445072922`).** Каждая скачанная
  серия один раз уходит в закрытый канал, а её `message_id`/`file_id` записываются в
  Firebase RTDB (ключ `anime/media/{release}-{серия}-{качество}`). Любой пользователь получает
  такую серию **моментально** — `copy_message` из канала, без скачивания и **без имени канала**
  (это копия, а не пересылка). Ссылка-источник: https://t.me/c/4445072922/42
* **Диск не забивается:** после успешной отправки mp4, превью и сегменты удаляются сразу
  (`DELETE_AFTER_SEND=1`) — при хранилище 512 МБ это важно, а мгновенная повторная выдача
  всё равно работает по `file_id` из базы.
* Подпись под видео — только название, серия, качество и размер (без служебных подробностей).

**Приём файлов (тоже до 2 ГБ)**
* Пришли боту видео/документ/аудио/фото — сохранит `file_id`, покажет размер.
* Кнопки: 📤 отправить обратно (мгновенно), 📥 скачать на сервер (прогресс),
  📁 список «Мои файлы» с пагинацией.

## 🌐 Умный роутинг по api_id / api_hash (если Telegram не пускает бота)

Бот перебирает пары **по состоянию, а не «по кругу»** (`credentials.py`):

| Что ответил Telegram | Что делает бот |
|---|---|
| `API_ID_PUBLISHED_FLOOD` (api_id «засвечен» в интернете) | пауза паре **6 часов**, берёт следующую — публичные пары бессмысленно долбить |
| `FLOOD_WAIT_30` и т.п. | пауза ровно столько, сколько просит Telegram (до `API_KEYS_FLOOD_MAX`) |
| `AUTH_KEY_UNREGISTERED`, `SESSION_REVOKED`, `API_ID_INVALID` | пара в длинную паузу (12 ч), сломанный файл сессии удаляется |
| сетевые ошибки / прокси | короткая пауза 60 с, пара не «хоронится» |

* **Память между перезапусками:** результат каждой пары лежит в `/data/sessions/cred_state.json`,
  поэтому после рестарта контейнера бот сразу поднимается на рабочей паре — без нового перебора.
* **Процесс не падает.** Если ни одна пара не пустила, бот ждёт с растущей паузой
  (1 → 2 → 5 → 10 → 30 мин) и пробует снова. Раньше процесс завершался, Railway перезапускал
  контейнер, и это как раз устраивало шторм попыток авторизации.
* **Смена пары на ходу:** если связь потерялась, бот сначала переподключается той же парой,
  а если Telegram её забанил — сам переходит на следующую.
* **Порядок:** своя (личная) пара → непроверенные → с меньшим числом отказов → пары в паузе в самом конце.
* Статус видно в боте: `/stats` → «API-пара» и «Пары api_id: доступно X из Y, публичных заблокировано Z».

### Как проверить пары вживую (одна команда)
```bash
python anime_bot.py --creds        # только «живые» пары (в паузе не трогает)
python anime_bot.py --creds-all    # проверить вообще все пары
```
Печатает таблицу: `✅ api_id=… — пускает, бот @…` / `❌ api_id=… — API_ID_PUBLISHED_FLOOD → пауза 6 ч`.

### ⚠️ Если ВСЕ пары — публичные
`API_ID_PUBLISHED_FLOOD` означает: «этот api_id опубликован в интернете, сервер ограничил его
для авторизации бота». Публичные пары клиентов Telegram (Android/iOS/Desktop/TDLib/web) режутся
почти всегда, сколько их ни перебирай. Лечится только своей парой:

1. https://my.telegram.org → **API development tools** → создать приложение (имя любое).
2. Вставить `api_id`/`api_hash` в `api_keys.py` → блок `PRIVATE_CREDENTIALS` (пробуется первым),
   **или** задать в Railway → Variables: `API_ID` и `API_HASH`.
3. Если репозиторий публичный — лучше вариант с Railway Variables: ключ, лежащий в открытом
   репозитории, со временем тоже станет «опубликованным».

## 🔥 Firebase RTDB: чтобы id видео точно сохранялись

Ключи проекта уже вшиты в `config.py` (`FIREBASE_CONFIG`), писать ничего не нужно. Но у новой
базы по умолчанию **закрытые правила** — тогда бот напишет в лог
«RTDB: запись запрещена правилами базы» и продолжит работать на локальном SQLite
(серии всё равно отдаются из канала, просто индекс не общий между перезапусками).

Чтобы включить общий индекс, открой Firebase → Realtime Database → Rules и разреши ветку:

```json
{
  "rules": {
    "anime": { ".read": true, ".write": true }
  }
}
```

Если правила должны требовать авторизацию — задай в Railway переменную `RTDB_AUTH`
(database secret из Firebase → Project settings → Service accounts → Database secrets) либо
оставь как есть: бот один раз попробует анонимный вход Firebase и, если не выйдет, продолжит на SQLite.

### `API_ID_PUBLISHED_FLOOD` — «ключ ограничен, потому что опубликован»
Telegram сам сообщает, что api_id засвечен в интернете. Бот отложит такую пару на 6 часов и
возьмёт следующую; если таких все — будет ждать и писать в лог, что нужна своя пара
(см. раздел «Умный роутинг» выше). Перебор публичных пар тут не помогает — только своя пара.

## 🧠 Как это работает под капотом

1. **Поиск.** `GET /api/v1/app/search/releases?query=…` (и резервно `/anime/catalog/releases?f[search]=…`).
2. **Релиз.** `GET /api/v1/anime/releases/{alias|id}` → список серий с готовыми HLS-ссылками
   (`hls_480`, `hls_720`, `hls_1080`), длительностью, таймингами опенинга/эндинга.
3. **Скачивание.** Сегменты m3u8 качаются параллельно (адаптивно: 3 → 8 потоков) в папку серии, затем
   ffmpeg собирает mp4 уже из локального плейлиста (copy, качество 1:1), считает прогресс по
   `-progress pipe:1`, делает превью-кадр (≤200 КБ, как требует Telegram) и чистит сегменты.
4. **Отправка.** Pyrogram (MTProto) грузит файл в Telegram напрямую — до 2000 МБ, с превью,
   длительностью, `supports_streaming` и клавиатурой «следующая серия / другое качество».
5. **Канал-хранилище + RTDB.** Готовое видео один раз отправляется в канал
   `TELEGRAM_CHANNEL_ID`, а `message_id`, `file_id`, размер и параметры — в Firebase RTDB
   (дублируются в SQLite). Повторный запрос любой серии любым пользователем — `copy_message`
   из канала: миллисекунды, без скачивания, канал в сообщении не виден. Локальный диск при этом
   чист — файл нужно скачать лишь один раз за всю жизнь серии.

## 🩺 Частые проблемы

| Симптом | Что делать |
|---|---|
| `AniLibria API недоступно` | Проверь сеть сервера/блокировки, задай `ANILIBRIA_MIRRORS` с рабочим зеркалом или `ANILIBRIA_PROXY` |
| Релиз «заблокирован по региону» | Нужен VPN/прокси (`ANILIBRIA_PROXY`) — это ограничение самого AniLibria |
| `FloodWait` в логах | Это нормально при перегрузке; бот сам ждёт и повторяет |
| Файл не влезает в лимит | Бот сам перейдёт на 720p/480p (`TRY_LOWER_QUALITY_ON_TOOBIG=1`) |
| Мало места на диске | Уменьши `MAX_CACHE_GB` (старое чистится по LRU автоматически) |
| Долго качается | Подними `HLS_CONNECTIONS` (12–16) — но CDN может начать резать соединения |
| «CDN AniLibria ограничил запросы» (429/403) | Уменьши `HLS_CONNECTIONS=4` и `HLS_START_CONNECTIONS=2`; на Railway выбери регион **EU West (Amsterdam)** — он ближе к CDN; файл докачивается той же кнопкой |
| Долгая сборка | Сборка идёт с локальных сегментов за секунды; долго только если включился транскод |
| Нужны логи | `docker compose logs -f`, либо `python anime_bot.py --check` |

## ⚠️ Безопасность и правовой момент

* **Токен и api_id/api_hash вшиты в код — как просили.** Если репозиторий публичный, лучше
  переопределять их через переменные окружения (`BOT_TOKEN`, `API_ID`, `API_HASH`),
  а вшитые значения держать только в приватной копии.
* В репозитории лежит `meowmessenger-firebase-adminsdk-*.json` — это **секрет Firebase**.
