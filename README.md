# Noir P2P — Android Java

Чёрный Android P2P-чат на Java. Проект собирается с **Android SDK 36**, `targetSdk 36`, `minSdk 26`, Java 21 и актуальным Gradle 9.4.1 / Android Gradle Plugin 9.2.0.

## Функциональность и статус рабочей ветки

Базовая версия уже содержит:

- Анонимную авторизацию Firebase через REST API; Firebase UID служит ID, которым собеседники обмениваются вручную.
- Firebase Realtime Database REST + SSE для WebRTC offer/answer, ICE-кандидатов и приглашений.
- Передачу текста и файлов напрямую через WebRTC DataChannel с DTLS/SCTP; содержимое не записывается в Firebase.
- Фото, видео, аудио/музыку, документы, голосовые заметки и запись короткого видео-сообщения («кружка»); вложения до 50 МБ.
- Локальную SQLite-историю, очередь исходящих сообщений при временном отсутствии P2P-канала и переподключение.
- Foreground-сервис типа `remoteMessaging`, уведомления, тёмный интерфейс, системный Photo/Document Picker и открытие медиа.

В текущей рабочей ветке дополнительно внесены, но **ещё не прошли Java-компиляцию и Android-тестирование**:

- Интеграция официального libsignal 0.105.0: Signal Protocol-сессии и шифрование текстов/файлов на уровне DataChannel; persistent protocol state защищается AES-GCM ключом Android Keystore. Для первого соединения используется TOFU; в чате добавлен просмотр SHA-256 отпечатка и ручная отметка сверки.
- AES-GCM шифрование текстов и имён файлов в локальной SQLite-истории с миграцией старых записей.
- Inline-превью до 12 последних изображений и декодирование превью с ограничением размеров.
- Inline reply и действия принять/отклонить в уведомлениях; очередь ответа до готовности авторизации.
- WebRTC-аудио- и видеозвонки с Signal-зашифрованным SDP/ICE в RTDB, входящими уведомлениями, экраном принятия/отклонения, mute/speaker, переключением камеры, foreground-типами microphone/camera и постоянным уведомлением активного звонка с действием «Завершить». Реальная связь между устройствами ещё не подтверждена.
- Настроен чистый JVM source-check в CI; последний успешный прогон был до добавления звонков. Source-check не упаковывает APK; workflow сборки APK остаётся gated вручную и по умолчанию отключён.

## Включить Firebase перед запуском

Проект использует переданную конфигурацию Firebase (`meow-874ce`). В Firebase Console нужно:

1. В **Authentication → Sign-in method** включить **Anonymous**.
2. Убедиться, что создана Realtime Database в регионе `europe-west1`.
3. Применить правила из `firebase/database.rules.json`:
   - Firebase CLI: `firebase login`, затем из корня проекта `firebase deploy --only database`;
   - или скопировать JSON в раздел **Realtime Database → Rules** и нажать **Publish**.

Без включённой анонимной авторизации приложение не сможет создать UID; без правил RTDB запросы будут отклонены. API key клиента не является секретом доступа к базе: безопасность обеспечивается Firebase Authentication и RTDB rules. Не заменяйте правила на открытый `.read/.write: true`.

## Как связать два устройства

1. Установите APK на оба устройства и запустите приложение.
2. Скопируйте свой UID на главном экране и передайте его собеседнику любым удобным способом.
3. Каждый добавляет UID второго через **Новый чат**. Если приходит неизвестное приглашение, его можно принять на главном экране.
4. Для установки WebRTC-канала приложение собеседника должно быть открыто или работать в разрешённом Android foreground-режиме. После подключения текст и вложения передаются напрямую.

UID анонимного Firebase-пользователя хранится на устройстве. Очистка данных приложения или переустановка создаёт новый UID; старый ID после этого использовать нельзя.

## ICE / TURN и бесплатный публичный резерв

В приложение встроены шесть публичных STUN URL (пять Google и Cloudflare) и пять TURN transport-вариантов Open Relay: UDP/TCP на портах 80 и 443, плюс TLS (`turns`) на 443. Для Open Relay используются временные TURN REST credentials с 7-дневным TTL, вычисляемые по публичному static-auth secret, который сам провайдер документирует для своего static-auth режима. См. [документацию Open Relay](https://www.metered.ca/tools/openrelay/).

Это **около 10 ICE-адресов, но не 10 независимых TURN-провайдеров**: пять TURN URL — это транспортные/портовые резервы одного глобального сервиса; STUN только помогает обнаружить внешний адрес и не ретранслирует медиа. Open Relay указывает лимит 20 ГБ TURN-трафика в месяц; публичный shared-auth не даёт персональной квоты или SLA, и провайдер может изменить доступ. Не полагайтесь на него как на гарантированный production-релей.

В интернете нет надёжного набора из десяти независимых бесплатных TURN-серверов с постоянными рабочими логинами: настоящая TURN-релейная передача расходует трафик, а публичные пары логин/пароль из старых списков часто отозваны. Официальный Open Relay для персональных short-lived credentials требует бесплатную регистрацию и API key; этот ключ нельзя безопасно встраивать в APK. Если нужна дополнительная независимая резервная площадка, настройте собственный TURN или добавьте креденшелы провайдера как `TURN_URLS`, `TURN_USERNAME`, `TURN_CREDENTIAL`. Учтите, что эти значения, если передать их при сборке клиентского APK, можно извлечь из приложения; для приватного аккаунта безопаснее выдавать краткоживущие credentials через backend.

Без рабочего TURN некоторые мобильные сети, CGNAT и корпоративные Wi‑Fi не смогут установить P2P-соединение. Публичный fallback — best effort, не абсолютная гарантия.

## Сборка, подпись и получение файлов через GitHub Actions

APK собирается **только в GitHub Actions**, не локально. На push/PR во время разработки выполняются только JVM unit tests (`testDebugUnitTest`), без упаковки APK. Release доступен вручную через **Actions → Android release APK и handoff → Run workflow**, с `build_apk=false` по умолчанию; ставить `true` следует только после завершения реализации и проверок.

CI использует Android SDK/target API 36, Java 21, R8 и только ABI `arm64-v8a`; workflow проверяет ABI, наличие mapping-файла, APK-подпись и отпечаток сертификата. `versionCode` равен возрастающему номеру GitHub Actions run, `versionName` — `1.0.<номер запуска>`.

Постоянный PKCS#12-keystore и пароль находятся в `handoff/NoirP2P-release-keystore.p12` и `handoff/NoirP2P-release-keystore-password.txt`; GitHub Actions читает их прямо из checkout, Actions Secrets для подписи не нужны. `signing/NoirP2P-release-cert.pem` — публичный сертификат, с ним сверяются подпись APK и keystore; alias — `noirp2p-release`. Инструкции и важное предупреждение — в [`signing/README.md`](signing/README.md).

После разрешённого ручного release-запуска в `handoff/` публикуются `NoirP2P-release.apk`, `NoirP2P-source.zip` и новая версия `releases/NoirP2P-<versionName>+<versionCode>.apk`. Предыдущие версии не удаляются. Текущий запуск также предоставляет APK/ZIP во вкладке **Artifacts** на 30 дней. Исходный ZIP не включает APK и прежние ZIP.

**Безопасность:** владелец попросил поместить приватный signing key и пароль в `handoff/`, поэтому они будут публичны вместе с исходниками и Git-историей. Любой сможет подписать вредоносное APK, которое Android сочтёт обновлением Noir P2P; это небезопасно и необратимо для уже опубликованных копий. APK содержит подпись/сертификат, а не сам приватный ключ. Более безопасный вариант — Actions Secrets.

Существующий `handoff/NoirP2P-debug.apk` оставлен как прежний артефакт; он не является release. Первый release будет подписан новым постоянным ключом, поэтому Android не сможет установить его поверх старого debug APK — до первого перехода сохраните важные данные и удалите debug-приложение.

## Незавершённые функции и ограничения

- Signal-интеграция и звонковый код в текущем checkout ещё не прошли Java-компиляцию. Звонки не проверены на двух Android-устройствах. Обоим собеседникам потребуется совместимая версия приложения; legacy-клиенты без Signal bundle не смогут обмениваться сообщениями или принимать эти звонки. Первый контакт использует TOFU: сверяйте полный SHA-256 отпечаток по независимому каналу. QR/SAS UI и безопасный сценарий повторной привязки после смены ключа пока не готовы.
- Звонковый signaling передаёт SDP и ICE-кандидаты через Signal Protocol и RTDB; media идёт через WebRTC DTLS-SRTP и зависит от NAT/TURN. Уведомления RTDB SSE не являются надёжным FCM push: если процесс остановлен, мгновенное пробуждение не гарантируется.
- Передача файлов реализует ограничение параллельности, ACK-окно, persisted offset и pause/resume; исходники и JVM tests проходили в предыдущем CI-прогоне, но обмен и восстановление передачи на двух реальных устройствах не проверены. Превью и notification actions также требуют проверки на устройстве.
- Signal-библиотека AGPL-3.0-only: см. [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md). Лицензию проекта нужно определить до распространения APK.
- Реальные Signal и WebRTC включают собственные JNI-библиотеки; ровно один `.so` в APK обещать нельзя. Приватные ключи хранятся зашифрованно через Android Keystore, а не помещаются в `libc++_shared.so`. Keystore может быть программным; аппаратная защита зависит от устройства.
- R8/resource shrinking затрудняют анализ release DEX и ресурсов, но не обеспечивают абсолютную защиту от декомпиляции. Проверки не запускаются внутри приложения.

Остальные ограничения ICE/TURN, фоновой работы Android и P2P-доставки описаны выше: результат зависит от сети, системных ограничений и реальных устройств, поэтому «100%» гарантию без тестов дать нельзя.

## Ограничения, важные для реального использования

- Android не позволяет гарантировать вечную фоновую работу: пользователь может остановить приложение, система — ограничить сеть/сервис, а производитель — агрессивно выгружать процессы. Foreground service с уведомлением и повторы улучшают стабильность, но не заменяют push.
- Сейчас входящий сигналинг слушается Realtime Database SSE foreground-сервисом. Если процесс полностью остановлен системой, мгновенное пробуждение чата требует отдельной настройки Firebase Cloud Messaging (FCM); в данном исходном проекте FCM не подключён.
- Для гарантированной связи между разными типами NAT нужен надёжный TURN relay. Файлы передаются P2P и не имеют серверной доставки/резервной копии: оба клиента должны быть доступны для установления DataChannel.
- Выпущенная базовая версия использовала DTLS для DataChannel. Рабочая ветка добавляет Signal E2E, но пока не прошла компиляцию и двухсторонний runtime-тест; до их прохождения не считайте её проверенной.
- Видео-кружок по-прежнему записывается как короткое видео-вложение и не связан с отдельной функцией live-видеозвонка.
