# Tsuyu Android

Tsuyu — персональный Android-мессенджер на Java. Поддержка Android 8–16 (`minSdk 26`, `compileSdk/targetSdk 36`); постоянный package name: `com.tsuyu.messenger`.

## Сборка и обновления

GitHub Actions workflow: `.github/workflows/android.yml`. Он собирает debug/release APK, публикует прямой файл **`app-release.apk`** и ZIP исходников в GitHub Release. После сборки из APK удаляются ненужные desktop/testing-библиотеки Signal, нативный код очищается от DWARF debug-данных, остаётся ABI **arm64-v8a**, затем APK выравнивается и подписывается. CI блокирует публикацию, если итоговый APK больше **30 000 000 байт**. Эмуляторы не запускаются. 32-битные устройства этой сборкой не поддерживаются. Debug APK имеет suffix `.debug` и не подходит для обновления release-версии.

Release APK подписывается постоянным `signing/tsuyu-release.p12`; `versionCode` автоматически растёт в CI. Владелец проекта явно выбрал хранение keystore и пароля в публичном Git. Это означает, что любой посетитель репозитория может получить ключ и подписывать APK как Tsuyu. Не используйте этот ключ для распространения приложения с чувствительными данными; если решение изменится, отзовите/замените ключ до публикации пользователям.

## Дизайн-система

Разбор проблем интерфейса и карта редизайна — в `DESIGN_AUDIT.md`. Кратко о том, как теперь устроен UI:

- **Палитра заморожена**: значения в `values/colors.xml` не менялись. Литералы, которые раньше жили прямо в layout'ах (`#99141416`, `#AA141416`, `#2C1616`, `#19191C`, иконные `#FFFFFFFF`), получили имена (`tsuyu_scrim`, `tsuyu_scrim_strong`, `tsuyu_danger_surface`, `tsuyu_skeleton`, `tsuyu_white`) с теми же значениями.
- **Геометрия — только через токены** `values/dimens.xml`: шкала отступов (4/6/8/12/16/20/24/32), радиусы (6/10/14/16/20/24/pill), тап-зоны, размеры аватаров, строк, медиа и разделителей. Хардкод `dp` в layout'ах больше не используется.
- **Типографика и компоненты** — `values/styles.xml`: `TextAppearance.Tsuyu.*` (логотип, заголовки, строки, подписи, метки времени, моно-код) и `Widget.Tsuyu.*` (кнопки Primary/Secondary/Quiet/Danger/IconButton/Chip, поля ввода, карточки, пузыри, заголовки шторок).
- **Тема** задаёт стили по умолчанию (`materialButtonStyle`, `materialCardViewStyle`, `toolbarStyle`, `bottomSheetDialogTheme`) и общие шейпы, поэтому новые экраны автоматически попадают в систему.
- **Ритм**: шапка 56dp с hairline-разделителем, строки списка 78dp с выравниванием текста по 84dp, пузыри с потолком текста 272dp и группировкой подряд идущих сообщений (зазор 6dp между блоками, 2dp внутри), анимации 200/240ms, пульсы 900/1600ms.
- Локальная проверка ресурсов без Android SDK: `python3 tools/check_resources.py` (ловит битые ссылки `@color/@dimen/@style/@drawable`, id из Java и родителей стилей).

## Firebase

Клиент использует только Firebase Authentication и Realtime Database; правила находятся в `database.rules.json`, конфигурация deploy — в `firebase.json`. После настройки Firebase:

```sh
firebase deploy --only database
```

Публичная Android client config (`FirebaseBootstrap`) используется для Auth/RTDB. Дополнительно release-сборка кладёт в `app/src/main/assets/fcm_sender_key.json` копию сервисного аккаунта проекта: без сервера именно телефон подписывает OAuth2-токен и отправляет push собеседнику (см. «Push без сервера»). Это Admin credential внутри APK — любой, кто распакует APK, получит доступ к проекту. Владелец проекта сознательно принял это ради работы без сервера; при утечке APK ключ нужно ротировать в Google Cloud/Firebase IAM. Workflow блокирует попадание файлов с именами `*service-account*.json` и `*firebase-adminsdk*.json` внутрь `app/`, поэтому копия названа иначе.

## Протокол и ограничения

- Личные сообщения используют официальный `libsignal-android`: PQXDH/Double Ratchet; приватные состояния шифруются локально ключом Android Keystore. Исходник instrumentation-теста round-trip присутствует, но workflow его не запускает: проверка Signal на устройстве ещё не подтверждена.
- RTDB хранит шифротекст сообщений и публичные prekey bundle. SHA-256 отпечатки можно сверять вне чата. При изменении ключа приложение блокирует отправку, пока пользователь не подтвердит новый отпечаток и не сбросит сеанс.
- Профильные поля и presence **ограничиваются правилами RTDB**, но это не клиентское шифрование профиля: Firebase/оператор проекта, имеющий административный доступ, может прочитать данные. Username, публичные настройки, ключи и presence также не скрыты end-to-end.
- Фото/видео/голосовые передаются Base64 внутри E2EE payload и RTDB; крупные вложения ограничены лимитом размера записи/трафиком RTDB. Firebase Storage не используется.
- Push отправляет само устройство: `notifications/FcmPushSender` после коммита сообщения в RTDB минтит OAuth2-токен сервисного аккаунта, читает `users/{peer}/fcmTokens` и вызывает FCM HTTP v1. Сообщения уходят data-only с `android.priority=HIGH`, телефон получателя (`TsuyuMessagingService`) идёт в RTDB, расшифровывает текст на устройстве и только затем рисует уведомление; шифротекст в уведомление не попадает. Плюс foreground-сервис `TsuyuSyncService` подстраховывает, когда приложение живо. Force-stop или агрессивная экономия батареи по-прежнему могут задержать доставку — это ограничение Android, а не приложения.
- Круглые видеосообщения («кружочки») записываются фронтальной камерой через CameraX (`ui/CircleCameraDialog`) и проигрываются круглым окном. P2P аудио-/видеозвонки пока не реализованы. Архивы `Meow-main (6)/(8).zip` с эталонной реализацией в checkout отсутствовали, поэтому точное совпадение с ними подтвердить нельзя.

Исходный handoff-архив версии находится в `handoff/` и исключает корневой Firebase Admin JSON.

## Офлайн-режим (v1.4)

Чат-лист и переписка больше не зависят от сети: приложение рисует интерфейс из локальной базы,
а сеть лишь дополняет её.

- `data/TsuyuStore.java` — SQLite-хранилище (`tsuyu-offline.db`): таблицы `chats` (диалог, превью,
  непрочитанные, закрепление, presence), `messages` (конверт сообщения + текст), `outbox`
  (очередь отправки) и `profiles` (профили собеседников). Все методы синхронизированы и
  выполняются вне UI-потока, кроме мгновенного чтения списка при старте.
- `crypto/LocalVault.java` — AES-GCM ключ в Android Keystore (на аккаунт). Тексты сообщений
  лежат в базе только в зашифрованном виде; расшифровка идёт на `cryptoQueue`.
- При входе `seedFromLocalCache()` сразу поднимает диалоги и профиль из базы, поэтому список
  чатов появляется мгновенно даже без интернета; RTDB-слушатели затем обновляют те же записи.
- Отправка: сообщение сначала попадает в `outbox` со статусом `pending`, после подтверждения
  RTDB переводится в `sent` (и `read` по квитанции). Очередь переигрывается при появлении сети
  (`.info/connected`) и при следующем запуске.
- Непрочитанные считаются по водяному знаку `(sent_at, message_id)`, поэтому повторные снапшоты
  не задваивают счётчик; открытие чата сбрасывает значок.
- В списке есть фильтр «Все / Непрочитанные», бейдж непрочитанных, закрепление, метки доставки
  последнего сообщения, а в переписке — разделители дат («Сегодня», «Вчера», «12 октября»)
  и кнопка возврата к последнему сообщению.

## Чаты (v1.5)

Список и экран переписки переработаны под привычки мессенджеров-лидеров:

- строка чата собрана в три колонки: аватар 54dp с индикатором онлайна, имя 16sp + превью 14sp,

- в шапке списка появились фильтры «Все / Непрочитанные» и баннер «Нет подключения»;
- формат времени строки: «HH:mm» для сегодня, «вчера», «12 окт» для остальных;
- в переписке добавлены разделители дат («Сегодня», «Вчера», «12 октября»), кнопка возврата
  к последнему сообщению и более крупная типографика шапки;
- меню чата (долгое нажатие в списке или ⋯ в переписке): профиль собеседника, закрепить/открепить,
  отметить прочитанным/непрочитанным, экспорт, код безопасности и очистка истории на устройстве.

## Push без сервера (v1.11)

Сервера у проекта нет, поэтому цепочка доставки целиком клиентская:

1. отправитель пишет шифротекст в RTDB (`ChatRepository.sendPayload`);
2. сразу после коммита `FcmPushSender` подписывает RS256-JWT сервисным аккаунтом, меняет его на
   access token в `oauth2.googleapis.com/token` (токен кэшируется ~55 минут) и читает
   `users/{получатель}/fcmTokens` — правила RTDB не пускают туда чужого пользователя, а admin-токен пускает;
3. на каждый токен устройства уходит одно FCM HTTP v1 сообщение с данными
   `{chatId, senderUid, messageId, senderName}` (без текста сообщения);
4. `TsuyuMessagingService` на телефоне получателя идёт в RTDB, расшифровывает payload своим
   Signal-сеансом и строит `MessagingStyle`-уведомление: аватар, имя, время отправки и текст;
   до расшифровки показывается «Расшифровка…», а не шифротекст;
5. «мёртвые» токены (404/410 от FCM) удаляются из RTDB автоматически.

CI проверяет цепочку на каждой сборке: шаг «Verify the bundled sender key really works with FCM
HTTP v1» подписывает JWT тем же ключом из `main`, получает access token и делает `validate_only`
отправку в FCM HTTP v1 (без доставки, без сервера), а шаг «Assert the release APK…» убеждается, что
в подписанном APK лежат `assets/fcm_sender_key.json` (хеш совпадает с репозиторием), класс
`FcmPushSender`, строки `messages:send`/`oauth2.googleapis.com/token` и расшифрованные уведомления.

Всплеск сообщений склеивается: push уходит один раз через 600 мс и всегда с самым новым id,
поэтому получатель не получает лавину уведомлений. Дубликаты дополнительно отсекает
`NotificationSounds.claimNotification`, общий с foreground-сервисом.

## Звонки без сервера (v1.16)

Аудио и видео звонки — чистый P2P: медиа идёт от телефона к телефону через WebRTC
(`io.github.webrtc-sdk:android`, линия M144), а сигналинг живёт в той же RTDB.

1. вызывающий пишет звонок в `chats/{chatId}/calls/{callId}` (`from`, `to`, `video`, `state`)
   и сразу предлагает SDP-оффер;
2. параллельно уходит страница о вызове двумя каналами: почтовый ящик
   `users/{получатель}/callInbox` (виден, когда приложение открыто) и мгновенный FCM-пуш
   (`type=call`) — он поднимает приложение, даже если оно выгружено из памяти;
3. `TsuyuMessagingService` показывает полноэкранное уведомление со звуком и вибрацией,
   `CallActivity` открывает экран звонка; кнопки «Ответить»/«Отклонить» работают из уведомления;
4. ICE-кандидаты обеих сторон летят в `calls/{callId}/ice/{uid}`, состояние — в `calls/{callId}/state`;
5. `calls/{chatId}/polls` — только голоса опросов; больше в правилах ничего не добавлено.

Релеи вшиты в код (`call/IceServers.java`): **10 публичных STUN и 11 TURN-«туннелей»** на портах
80/443 (UDP, TCP и TLS), включая `openrelay.metered.ca`, `global.relay.metered.ca` и `freestun.net`.
ICE пробует их по очереди и берёт первый рабочий, поэтому звонок не рвётся за файрволом и в
мобильной сети без «белого» IP. Если сеть сменилась и соединение просело, `restartIce()`
поднимает его заново вместо обрыва; при полном отказе звонок закрывается как «нет ответа».

Стабильность в фоне: `CallService` — foreground-служба типа `phoneCall|microphone|camera`
с блокировкой процессора и Wi-Fi, плюс `FLAG_KEEP_SCREEN_ON` на экране разговора. Уход с экрана
звонок не прекращает — он остаётся в шторке с кнопкой «Завершить». Через 45 секунд дозвона
вызов сам закрывается как пропущенный.

Итог разговора пишется в переписку как обычное (шифрованное) сообщение с kind `call`:
направление, длительность и пометка «видео». У вызывающего — своя строка, у собеседника — входящая,
дублей нет.

## Опросы, сгорание, отложенная отправка, обои, стикеры (v1.16)

- **Опросы:** меню вложений → «Опрос» (до шести вариантов). Голоса хранятся в
  `chats/{chatId}/polls/{messageId}/{uid}`, пузырь показывает проценты и ваш выбор, тап меняет голос.
- **Таймер сгорания:** меню вложений → «Сгорание» (5 с … 1 день). Следующее сообщение получает
  оранжевый пунктирный пузырь и бейдж с остатком; когда время вышло, сообщение исчезает из базы
  (автор удаляет его, у собеседника оно пропадает тем же таймером).
- **Отложенная отправка:** «Позже» — сообщение из поля ввода уходит само в выбранный момент
  (`AlarmManager` + `ScheduledSendReceiver`, шифрование тем же Signal-сеансом; сервера нет).
- **Обои:** меню чата → «Обои чата» и настройки → «Обои для всех чатов». Картинка хранится на
  устройстве, чат перекрывает общие обои.
- **Редактор стикеров:** кнопка стикера → рисование пальцем, щипок — масштаб, ползунок порога
  вырезает фон по яркости, результат уходит PNG-стикером с прозрачностью.
- **Поделиться контактом:** меню вложений → «Контакт», визитка уезжает как сообщение.
- **Исключения защиты:** «Защита от скриншотов» остаётся глобальной, но в выбранных чатах
  (меню чата → «Исключение защиты») `FLAG_SECURE` снимается, а в остальном приложении — нет.

## Приоритет мобильного трафика (v1.17)

Приложение по умолчанию говорит через **обычный мобильный интернет**, а не через Wi-Fi — так
просил владелец, и так звонки стабильнее в дороге:

- `call/NetworkPriority` находит сотовую сеть с подтверждённым интернетом
  (`TRANSPORT_CELLULAR` + `NET_CAPABILITY_VALIDATED`) и привязывает к ней весь процесс
  (`ConnectivityManager.bindProcessToNetwork`). Это системный механизм: через мобильную сеть идут
  и медиа-сокеты WebRTC, и Realtime Database;
- привязка держится, пока есть мобильная сеть: появился Wi-Fi — процесс всё равно остаётся на
  сотовой сети; пропала сотовая — привязка снимается сама (сокеты возвращаются к Wi-Fi), а когда
  сотовая вернётся, `NetworkCallback` привяжет процесс к ней снова;
- звонок поднимает приоритет на своём старте и возвращает его после разговора;
- если на текущей сети ICE не сложился, звонок не рвётся: сначала меняется сеть (мобильная ↔ Wi-Fi),
  затем один раз перезапускается ICE; на экране видно «Переключаю на мобильный интернет…» или
  «Переключаю на Wi-Fi…»;
- на экране звонка бейдж показывает, через что идёт разговор: `P2P · релеев: 11 · мобильный интернет`;
- выключить приоритет можно в настройках («Сеть» → «Мобильный трафик в приоритете»), там же видно
  текущее состояние: `мобильный трафик`, `Wi-Fi` или `мобильной сети нет`.

Разрешения: `ACCESS_NETWORK_STATE` и `CHANGE_NETWORK_STATE`.

## Резервный канал звонков (v1.18)

Правила Realtime Database со узлом `calls` публикуются из CI (`tools/update_database_rules.py`), но
сервисный аккаунт может не иметь права на их публикацию — тогда база какое-то время живёт по
прежним правилам, где `calls` ещё нет. Чтобы звонки работали в любом случае, сигналинг идёт сразу
по двум путям:

1. основной узел `chats/{chatId}/calls/{callId}` (появляется после публикации правил);
2. резервный ящик `chats/{chatId}/typing/{uid}/call/{callId}` — узел `typing/{uid}` уже разрешён
   правилами (каждый пишет только своё, читают оба участника).

Оба канала пишутся и оба слушаются, дубликаты отсекаются (`appliedCandidates`, флаги
`appliedRemoteDescription`). Индикатор набора текста больше не сносит узел `typing/{uid}` целиком —
он трогает только свои поля `typing`/`at`, поэтому резервный ящик не пропадает. После разговора
ящик вычищается с задержкой в 4 секунды, чтобы «звонок завершён» успел дойти до собеседника.

## Свой чистый P2P без сторонних библиотек (v1.22)

Все сторонние P2P/WebRTC-библиотеки из проекта **удалены**. Звонки теперь собраны на
встроенных средствах Android (пакет `com.tsuyu.messenger.p2p`):

- `Stun` — свой STUN-клиент (RFC 5389) на обычных сокетах: узнаём, как нас видит интернет;
- `PeerLink` — прямой UDP-канал между телефонами: «пробивка» NAT, подтверждения,
  свои ключи (AES-256-GCM, ключ выводится из идентификатора звонка и двух случайных чисел),
  чужой трафик отбрасывается, повторные пакеты не принимаются, при пропаже связи канал
  один раз пересобирается с новым портом;
- `VoiceEngine` — голос: микрофон и динамик Android (8 кГц моно, кадр 20 мс) с буфером
  переупорядочивания: 128 кбит/с идёт через обычный мобильный интернет;
- `VideoEngine` — видео: камера (Camera2) → кодировщик H.264 (MediaCodec) → пакеты по
  900 байт → декодер собеседника прямо на SurfaceView. Всё завернуто так, что если камера
  или кодек не подошли, видео отключается, а голос продолжается;
- `P2pCall` — сам звонок: обмен адресами и состояниями идёт через Realtime Database
  (основной узел `calls` плюс резервный ящик в `typing`), а сам разговор — строго напрямую
  между телефонами. Звук включается только после того, как трубку взяли.

Серверов по-прежнему нет: база используется только для знакомства телефонов, дальше
пакеты идут напрямую, и их нельзя прочитать по дороге (AES-256-GCM).

## v1.30 — мгновенный UI: без дублей, без ожидания, с анимациями списков

- **Дубли закрыты на корню.** Строка опознаётся в первую очередь по номеру отправителя

  это одна строка и в переписке, и в сравнении строк (DiffUtil). Подтверждение больше не
  добавляет вторую строку и не «прыгает».
- **Отправка выглядит отправленной сразу.** Пузырь с первого кадра выглядит как обычное

- **Перерисовка — в тот же кадр.** `requestMessageRender` и `requestChatListRender` на главном

  даты). Список чатов при том же составе и порядке обновляет только изменившиеся строки.
- **Даты больше не создают объекты на каждый кадр.** Форматтеры и календари в обоих списках
  создаются один раз.
- **Анимации списков вернулись** — штатные анимации вставки и сдвига; смена содержимого строки
  идёт без «мигания». Переходы между экранами по-прежнему мгновенные, без анимаций.
- Цвет пузыря — прежний яркий синий (как до затемнения).

## v1.33 — по техническому разбору: что применено из кода

- **Полностью убран `notifyDataSetChanged()`** (последний оставался в списке результатов поиска):
  строки обновляются по одной — вставка, удаление и изменение своих строк.
- **Аппаратные кадры для показа**: фото в пузырях и аватары списка декодируются сразу в память
  видеокарты (кадровый буфер не гоняется через обычную память). Там, где кадр потом сохраняют
  или рисуют на холсте (просмотр фото, редактор стикеров, обои), режим остаётся обычным —
  иначе сохранение снимка стало бы невозможным. Если телефон не отдал кадр в память видеокарты,
  автоматически берётся обычный.
- **Голосовой канал без мусора**: `PeerLink` умеет отправлять пакет прямо из общего буфера,
  поэтому на каждом кадре (каждые 20 мс) больше не создаются новые массивы.
- Проверено по коду и подтверждено: `System.gc()` в проекте нет; статических ссылок на экран
  (`Activity`) или `Context` нет; расшифровка в отрисовке строк отсутствует — в адаптер приходит
  уже готовый текст; разметка работает от края до края с учётом системных панелей и клавиатуры;
  типы фоновых служб в манифесте заданы (`phoneCall|microphone|camera`, `remoteMessaging`);
  тема — Material 3 с переключателем системных цветов; ключи хранятся через AndroidKeyStore.

## v1.34 — главный поток и потоки звонка по техническому разбору

- **Настройки больше не читаются из файла в главном потоке.** Все обращения к настройкам
  (`tsuyu_settings`) на экранах переведены на память настроек: чтение — из памяти, запись —
  сразу в память и в файл. Прямых обращений к файлу не осталось ни одного (проверено по коду).
  Службы (`TsuyuSyncService`, `TsuyuMessagingService`) и «режим невидимки» подключают настройки
  при старте, поэтому их чтения тоже идут из памяти.
- **Память настроек сама себя чинит:** появились `ensure` (подключение до входа в аккаунт)
  и `reload` (перечитать файл после групповых записей), поэтому память и файл не расходятся.
- **Потоки звонка стали управляемыми.** Циклы приёма пакетов, «пробивки», записи и
  воспроизведения звука, разбор кадров видео жили на самостоятельно созданных потоках и могли
  накапливаться от звонка к звонку. Теперь у каждого цикла свой именованный поток, который
  закрывается вместе с каналом (`P2pThreads.loop` / `P2pThreads.shutdown`).
- Проверено: самовольных потоков (`new Thread`) в коде приложения больше нет — все потоки
  создаются в одном месте (`util/Background`, `p2p/P2pThreads`).
